# 业务逻辑漏洞（原理篇）

## 一句话理解
逻辑漏洞不是代码写错了，而是**设计假设错了**：开发者假设用户会按预期顺序、预期次数、预期身份使用系统，攻击者偏不。

## 为什么扫描器扫不到
| 维度 | 代码层漏洞（SQLi/XSS 等） | 逻辑漏洞 |
| --- | --- | --- |
| 特征 | 有明确的语法/payload 特征 | 请求本身完全合法 |
| 检测 | 规则匹配即可 | 需要理解业务语义 |
| 误报 | 相对可控 | 自动化几乎必然误报 |
| 发现方式 | 扫描器 + fuzz | 人工梳理业务流程 |

逻辑漏洞是"人"的主场，这也是为什么 SRC 高分漏洞里逻辑类占比一直很高。

## 根因分类学
### 1. 信任客户端输入
- 金额、数量、角色、状态从请求里直接取值
- 前端 JS 校验被视为"校验"（绕开前端就裸奔）
- 隐藏字段、disabled 控件照样可提交

### 2. 状态机缺陷（步骤跳跃）
- 业务流程是"第 1 步 -> 第 2 步 -> 第 3 步"，但每个接口独立鉴权
- 攻击者直接请求第 3 步，跳过付费/验证环节
- 状态校验应在服务端维护（session 里记"已完成第几步"），而非依赖"用户拿不到后续接口地址"

### 3. 并发假设
- "先查余额再扣款"两步之间存在时间窗
- 单线程思维写出的代码，在并发请求下校验失效
- 防御靠数据库层：事务、行锁、唯一约束，而不是应用层 if-else

### 4. 边界假设
- 金额为正、数量为正、次数有限、时间有序——全是"应该不会有人乱来吧"
- 负数、零、溢出、极大值、类型混淆（字符串 vs 数字）都能打破假设

### 5. 身份与归属假设
- "能访问这个接口的人，就是该操作这个对象的人"
- 这是越权/IDOR 的根因，展开见 [EXP-IDOR](../exp/EXP-IDOR.md)

## 高频业务场景清单
场景千变万化，根因只有上面五类。下面按业务域列出高频场景，每条一句话点出根因（括号标注对应分类），利用手法与报文示例见 [EXP-Logic](../exp/EXP-Logic.md)。

### 支付类
- 金额篡改：前端计算的价格/优惠后金额直接提交（hidden 字段 / JSON `amount`），服务端不重算，改 0 元、负数、0.01 元皆可下单（信任客户端）
- 订单状态跳跃：取消订单后直接请求发货/收货接口仍能发货，订单状态机未在服务端校验（状态机）
- 货币精度截断：分/元换算或舍入方向不一致，小额多次转账套利（边界）
- 并发退款：同一订单并发发起多笔退款，"校验-扣减"非原子（并发）

### 账户类
密码重置是重灾区，全流程缺陷清单：
- token 可预测：时间戳/自增/弱随机生成，配合无频率限制即可枚举（边界）
- token 不绑定账号：拿自己的 token 改别人的密码（归属）
- Host 头投毒：重置链接域名取自 `Host` 头，受害者点击后 token 落到攻击者域名（信任客户端）
- 短信验证码 4-6 位且无尝试限制：直接爆破，无锁定无滑块（边界）
- 响应包返回验证码/校验结果可篡改：改 `{"code":1}` 为 `{"code":0}` 即过（信任客户端）

其他账户类：
- 手机号/邮箱改绑不校验原持有者：改绑接口直接传"目标账号 + 新手机号"即可接管（归属）
- 解绑后旧绑定凭证仍有效：旧邮箱/手机号还能收通知、走找回流程（状态机）
- 账号注销后数据残留：注销只打标记，历史订单、会话、Token 仍可访问（状态机）

### 验证码类
- 图形验证码不过期/可复用：验证一次不销毁，同一码无限重放（状态机）
- 短信轰炸：发送接口无频率限制，或限制在前端/Cookie 计数，并发+清 Cookie 绕过（边界）
- 语音验证码：无频率限制且响应包回显验证码，播报即泄露（信任客户端）
- 邮箱轰炸：注册/订阅/邀请接口无频率限制与图形码，脚本批量骚扰（边界）

### 会员/积分类
- 签到重放：重复请求签到接口无限领积分，接口不幂等（并发）
- 积分负数：兑换数量/积分为负，余额反向增加（边界）
- 抽奖概率篡改：中奖概率、奖品列表由前端返回控制，改包必中（信任客户端）
- 等级特权越权：低等级账号直接请求高等级专属接口，接口无等级校验（归属）

### 其他
- 时间戳依赖：限时价格/活动直接信任请求里的时间参数，改包即享早鸟价（信任客户端）
- 步数/GPS 运动数据伪造：健康活动直接提交步数、轨迹，服务端不校验设备来源（信任客户端）
- 邀请返利刷单：奖励发放不与真实转化绑定，批量注册自邀自刷（边界）

## 测试方法论
逻辑漏洞的产出不靠灵感，靠流程。四种方法由粗到细：先用时间线看全局，再用状态机抠跃迁，然后用对比找功能面差异，最后用并发开时间窗。

### 1. 时间线梳理法
把目标业务全流程按时间轴铺开，例如电商：注册 → 登录 → 浏览 → 下单 → 支付 → 发货 → 收货 → 退款 → 注销。

对时间线上**每个节点**问三个问题：

1. **可否跳过**：直接请求下一环节的接口、跳过当前环节会怎样（跳过支付直接发货）？
2. **可否回退**：请求已完成环节的旧接口会怎样（订单完成后重放取消）？
3. **可否并发重放**：同一请求同时发两遍会怎样（并发下单、并发退款）？

电商订单时间线示例：

| 节点 | 关键接口 | 可否跳过 | 可否回退 | 并发重放测试点 |
| --- | --- | --- | --- | --- |
| 注册 | `/register` | —— | 重复注册能否占用他人手机号 | 并发批量注册刷邀请返利 |
| 下单 | `/order/create` | —— | 取消后能否复用旧单号复活 | 并发下单超占库存 |
| 支付 | `/pay/submit` | 0 元/改价能否直接过 | 已支付能否改回待支付 | 并发重复支付回调 |
| 发货 | `/order/ship` | 未支付能否直接请求发货 | 已取消订单能否再发货 | —— |
| 退款 | `/refund/apply` | 超期订单能否仍退款 | 已退款能否再退一次 | 一单并发多笔退款 |
| 注销 | `/account/close` | —— | 注销后旧会话/Token 是否仍有效 | —— |

表里每一个"能否"都是一个具体测试点，逐格填空就是完整的测试计划。

### 2. 状态机审计法
订单、工单、提现单这类有状态流转的业务，先画出状态机，再逐一检查所有状态组合里哪些是**非法跃迁**——服务端是否只校验了登录态，而没有校验"当前状态才能进入下一状态"。

订单状态机（文字示意）：

```text
待支付 ──支付成功──> 已支付 ──发货──> 已发货 ──确认收货──> 已完成
  │                   │
  └──用户取消──> 已取消 └──申请退款──> 退款中 ──打款──> 已退款
```

合法跃迁之外的组合都是攻击面：

- 已退款 → 已发货？（退款到账后订单还能再发货）
- 已取消 → 已支付？（已取消订单重放支付回调"复活"）
- 退款中 → 已退款（无二次确认直接到账）

攻击 payload 示例（重放旧请求）：先用正常流程把订单推进到"已发货"并抓包保存发货请求；再对该订单走完退款流程至"已退款"；最后原样重放发货请求，观察服务端是否校验订单当前状态：

```http
POST /api/order/ship HTTP/1.1
Host: shop.example.com
Cookie: session=eyJ1c2VyIjoxMDI0fQ==

{"order_id": "20260913001"}
```

若响应 `{"code": 0, "msg": "ok"}` 且订单重新变为"已发货"，则确认存在非法跃迁——服务端只校验了登录态与归属，没有校验状态机。

### 3. 对比审计法
逻辑漏洞常藏在"视角差"和"版本差"里。

**三视角功能面对比**——同一业务用三种身份各过一遍，对比功能面差异：

| 视角 | 操作姿势 | 关注差异 |
| --- | --- | --- |
| 正常用户 | 按界面引导一步步操作 | 界面流程暴露了哪些接口与参数 |
| 管理员 | 直接调用后台/内部接口 | 内部接口是否只靠"菜单不可见"保护 |
| 黑产 | 无视界面，直接构造/篡改/重放请求 | 每个接口的独立鉴权、频率与状态校验 |

**新旧版本接口对比**——新版上线后老接口常未下线，而老接口往往没带上新版的修复（金额校验、频率限制、签名）。找法：App 历史版本抓包、前端 JS 里的旧路由、`/api/v1/` 与 `/api/v2/` 并存；用老接口打新数据。

### 4. 并发场景设计
四类高频并发测试点：

| 并发目标 | 测试姿势 | 预期缺陷 |
| --- | --- | --- |
| 优惠券 | 一张券并发发起多笔下单 | 一券多用、超额抵扣 |
| 库存 | 1 件库存并发下多单 | 超卖 |
| 余额 | 100 元余额并发提现/转账 100 元 | 余额为负、重复出款 |
| 签到 | 并发重复请求签到接口 | 积分/奖励重复发放 |

Burp Turbo Intruder 一句命令（所有请求在 gate 处对齐后同时放行，逼近服务端校验时间窗）：

```python
for i in range(50): engine.queue(target.req, gate='race')   # 50 个请求先在 gate 处挂起
engine.openGate('race')                                     # 同一瞬间全部发出
```

## 与代码层漏洞的关系
- 逻辑漏洞常与技术漏洞组合放大：越权 + XSS、竞争 + 支付、弱随机 + 密码重置
- 技术漏洞偏"点"，逻辑漏洞偏"线"（流程）——审计时要既能蹲下来看点，也能站起来看线

## 方法论沉淀
测试逻辑漏洞的正确姿势是"角色扮演"：
1. 假设你是一个想占便宜但完全守规矩（不发任何非法报文）的用户
2. 梳理业务流程图，标出每个环节的"信任假设"
3. 逐个假设问：如果我违反它，服务端会拦我吗？

利用手法、工具（Turbo Intruder 等）见 [EXP-Logic](../exp/EXP-Logic.md)。
